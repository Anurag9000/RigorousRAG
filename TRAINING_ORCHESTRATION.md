# RigorousRAG authoritative training orchestration

`python run_all_training.py` is the repository root for exhaustive scientific workload orchestration.

This document records the source contract implemented by the root launcher, the repository-owned workload catalog, the training/data/evaluation authorities, and the literal OPF_ADP resource scheduler. It describes source behavior; it is not a claim that models or datasets have been executed.

## 1. Ownership boundaries

RigorousRAG deliberately separates **scientific workload construction** from **machine-resource scheduling**.

- `run_all_training.py` builds the strict universal-controller profile and invokes the current local v23 bootstrap.
- `training/authoritative_training_suite_catalog.py` is the closed-world scientific job authority for RigorousRAG.
- repository training/data/evaluation CLIs own model, dataset, objective, checkpoint, metric and provenance semantics.
- `tools/universal_training_controller_entry.py` loads the shared v23 orchestration/audit layers.
- the literal byte-pinned `OPF_ADP` runner remains the sole resource/admission/process-control implementation.

No RigorousRAG layer reimplements OPF scheduling.

## 2. Default closed-world training matrix

The catalog contains exactly 17 training recipes. It validates the actual recipe JSON identity before emitting a job, so a config override cannot silently turn one advertised recipe into another architecture or variant.

### Classical learners — 4

1. `train:classical:fusion-weight`
   - authority: `training/authoritative_classical_training_cli_v3.py`
   - kind: `fusion_weight`
   - model: weighted score fusion
   - task: score fusion
2. `train:classical:listwise-fusion`
   - kind: `listwise_fusion`
   - model/objective: ListNet listwise fusion
3. `train:classical:domain-classifier`
   - kind: `domain_classifier`
   - task: query-domain classification
4. `train:classical:plan-ranker`
   - kind: `plan_ranker`
   - task: query-plan pairwise ranking

These optimizer-free learners retain the repository's transactional exact-resume implementations. Their state authorities persist bounded progress plus current/best parameters and early-stopping state rather than pretending to have a framework optimizer checkpoint.

### Retrieval learners — 9

All use `training/authoritative_retrieval_training_cli_v2.py`, which performs fail-closed external-input/model/tokenizer preflight and delegates optimization/checkpoint semantics to the sole retrieval engine.

5. `train:retrieval:dense-base` — dense bi-encoder, base objective
6. `train:retrieval:dense-distilled` — dense bi-encoder, teacher-distilled objective
7. `train:retrieval:splade-base` — SPLADE base
8. `train:retrieval:splade-distilled` — SPLADE teacher distillation
9. `train:retrieval:unicoil-base` — uniCOIL base
10. `train:retrieval:unicoil-distilled` — uniCOIL teacher distillation
11. `train:retrieval:colbert-base` — ColBERT base
12. `train:retrieval:colbert-distilled` — ColBERT teacher distillation
13. `train:retrieval:cross-encoder-listwise` — listwise cross-encoder reranking

The retrieval engine uses manifest-bound train/validation datasets, deterministic resumable sampling, checkpointed optimizer/scheduler/scaler/RNG/progress state where applicable, validation evaluation and validation-loss early stopping.

### Advanced RAG learners — 4

All use `training/authoritative_advanced_training_cli.py` and the existing advanced operator/runners.

14. `train:advanced:grounded-causal` — grounded generation with a causal LM
15. `train:advanced:grounded-seq2seq` — grounded generation with a seq2seq LM
16. `train:advanced:dynamic-causal` — dynamic-RAG policy with a causal generator
17. `train:advanced:dynamic-seq2seq` — dynamic-RAG policy with a seq2seq generator

The two seq2seq entries are not synthetic variants: the canonical advanced recipe/runner authority explicitly supports both `causal_lm` and `seq2seq_lm` generator families.

Advanced training persists `training_result.json` atomically beside its authoritative checkpoint root. This brings the advanced family onto the same stable downstream result contract already used by classical and retrieval training.

## 3. Explicit per-training lifecycle

Every one of the 17 training jobs has three explicit successors generated by the same catalog:

`training -> validation -> artifact/readiness testing -> metrics`

Therefore the default closed-world core contains:

- 17 training jobs;
- 17 post-training validation jobs;
- 17 artifact/readiness test jobs;
- 17 metrics materialization jobs;
- 7 calibration jobs;
- **75 jobs total before operator-enabled external lifecycle jobs.**

`training/authoritative_training_suite_postprocess.py` owns the three post phases.

### Validation

The postprocessor verifies the persisted training-result digest and binds it back to the exact training-config SHA-256. Advanced RAG additionally reuses the canonical advanced config validator and verifies the authoritative best/latest checkpoint against the run config.

### Artifact/readiness testing

This phase verifies that a produced artifact/checkpoint can be reconstructed through its native authority. It is intentionally **not** presented as held-out scientific testing when no held-out test cohort was declared. Retrieval verifies its content-addressed best/latest checkpoint. Advanced verifies its authoritative checkpoint/run binding. Classical verifies its transactional v3 result artifact.

When a real governed benchmark/test cohort is supplied, the separate benchmark/evaluator lifecycle jobs described below provide the scientific testing/evaluation path.

### Metrics

The postprocessor does not invent a universal scalar metric. It preserves the native trainer result and materializes an atomic index containing every finite numeric metric emitted by that result. Domain-native metrics therefore remain authoritative.

## 4. Deterministic calibration/materialization matrix — 7

`training/authoritative_calibration_cli.py` owns seven deterministic held-out-score fitting operations. They are non-training lifecycle jobs and use restart-exact/idempotent semantics rather than fake early stopping.

1. `evaluation_histogram`
2. `evaluation_conformal_nonconformity`
3. `evaluation_conformal_retrieval`
4. `retrieval_split_conformal`
5. `threshold_decision`
6. `confidence_isotonic`
7. `cross_profile_isotonic`

Each now has a concrete config under `config/calibration_*.example.json`.

Retrieval-specific calibrators depend on retrieval metrics. General calibration operations depend on the full post-training metrics frontier, so OPF/DAG execution cannot start them before upstream training artifacts exist.

## 5. Dataset acquisition without weakening local scientific authority

Downstream RigorousRAG ingestion is intentionally local-only and digest-bound. The repository does not declare one fixed set of truthful public dataset URLs, so the runner does not fabricate them.

`training/authoritative_dataset_fetch_cli.py` provides the optional upstream acquisition authority when a dataset does have a declared remote source. Its config schema is `rigorousrag-authoritative-dataset-fetch/v1`.

For every declared artifact it requires:

- a stable dataset/source ID;
- one or more credential-free HTTPS mirrors;
- a non-placeholder expected SHA-256;
- a repository-relative output path;
- a maximum byte bound.

It enforces HTTPS across redirects, streams into a temporary file, rejects oversized or digest-mismatched bytes, atomically publishes only verified content, refuses to overwrite a mismatching existing file, reuses an already matching file, and emits a content-addressed fetch receipt.

The fetched bytes are **not automatically considered scientifically admitted**. They still flow through the appropriate governed publication/import authority below, which owns license, schema, dataset-card, split and provenance semantics.

A template is provided at `config/dataset_fetch.example.json`. A production suite may add the fetch CLI as an enabled `setup` job in its `lifecycle_jobs` list and make governed imports depend on it.

## 6. Governed data and preprocessing authorities

`config/training_suite.example.json` records executable lifecycle templates. They are disabled by default because their exact local paths, SHA-256s, licenses, cohorts and policies are external scientific inputs. Enabling a job schedules the real command through the same OPF DAG; enabling a child without its parent fails catalog DAG validation.

The manifest currently represents the following concrete repository authorities.

### Grounded data

- scale-guarded governed grounded import;
- grounded canonical-v2 materialization;
- grounded canonical training bundle;
- grounded canonical recipe-v2/resolved training plan.

### Dynamic-RAG data and supervision

- governed dynamic trajectory dataset publication;
- SQLite information-need sidecar publication;
- SQLite realized-gain sidecar publication;
- SQLite logged-value sidecar publication;
- SQLite counterfactual sidecar publication;
- snapshot-keyed dynamic feature-observation sidecar publication;
- recorded runtime dynamic cohort publication;
- dynamic canonical-v2 materialization;
- recorded-dynamic canonical-v2 materialization;
- dynamic canonical training bundle;
- dynamic canonical recipe-v2/resolved training plan.

The canonical dynamic path uses exact local causal/seq2seq generator and tokenizer bindings and worker-local immutable SQLite supervision providers. Grounded materialization uses the governed grounded import receipt plus exact tokenizer/model/cache identities.

## 8. Production overrides

The default suite file is:

`config/training_suite.example.json`

A production suite can be selected without changing source:

```bash
RIGOROUSRAG_TRAINING_SUITE_CONFIG=config/production/training_suite.json python run_all_training.py
```

A production suite may:

- override any of the 17 training recipe config paths by exact training job ID;
- override any of the seven calibration config paths by calibration kind;
- enable and parameterize concrete governed setup/preprocess/validation/testing/metrics/release jobs.

The catalog rejects unknown training job IDs, unknown calibration kinds, source paths that leave the repository, missing enabled local executable sources, duplicate job IDs, duplicate executable commands, dangling/self dependencies and DAG cycles.

Config overrides are semantically checked. For example, the `dense-distilled` slot must still resolve to a dense/distilled retrieval config; a ColBERT or base config cannot silently occupy that identity.

## 9. Generic discovery is intentionally disabled for RigorousRAG

The universal controller can discover lifecycle scripts heuristically, but many RigorousRAG production CLIs require mandatory content-bound arguments. Running such CLIs with no arguments is incorrect.

The root profile therefore sets `disable_lifecycle_orchestration=true` and uses the explicit repository-owned suite catalog for every scheduled phase. Source/workload/model/registry audits remain enabled.

The three PEP-621 training console commands are aliases of the same authoritative source files used by the catalog. They are excluded from duplicate console-job materialization; they are not exemptions from model/source reachability.

## 10. Strict source and workload gates

The root profile keeps these controls fail closed:

- strict repository coverage;
- native resume evidence;
- exact training resume evidence;
- training early-stopping evidence;
- well-formed early-stopping exemptions for non-training phases only;
- runtime DAG enforcement;
- model-surface accounting;
- workload/config/registry accounting;
- member-level registry accounting;
- literal OPF mechanism parity.

The catalog additionally has its own closed-world assertions requiring exactly the 17 training IDs and seven calibration kinds listed in this document.

## 11. Early stopping

Early stopping is never synthetically injected by the central controller.

- retrieval and advanced neural trainers use their native validation evaluators and configured patience/min-delta behavior;
- classical learners retain their native resumable early-stopping state;
- deterministic setup/preprocess/calibration/postprocess jobs explicitly state that early stopping is not applicable.

If a future training authority is added without real early stopping, strict orchestration should fail until the actual trainer is implemented accordingly.

## 12. Resume and interruption semantics

Training jobs retain their native state authorities:

- neural retrieval/advanced paths use content-addressed checkpoints and exact progress/state restoration;
- classical optimizer-free learners use transactional state stores with cursor/order/current+best parameter/validation/early-stop state;
- deterministic non-training lifecycle phases use restart-exact semantics.

The shared exact-resume auditor remains responsible for proving these claims from reachable repository source and declared contracts before scheduling under strict mode.

## 13. Literal OPF scheduler mechanisms

RigorousRAG does not copy these mechanisms. Once the scientific DAG is compiled, the byte-pinned OPF_ADP implementation owns all of them:

1. GPU-first admission and explicit launch-device selection;
2. active-job and active-GPU-job ceilings;
3. resource-bounded concurrency when explicit concurrency is zero;
4. live-editable concurrency control;
5. start-index/job-limit slicing;
6. RAM stop/resume thresholds;
7. VRAM stop/resume thresholds;
8. swap pressure thresholds and hysteresis;
9. launch-time host-RAM and VRAM reserves;
10. runtime child-process RSS and VRAM footprint measurement;
11. child-footprint safety buffers in admission/gate closing;
12. separate host and GPU pressure domains;
13. suspension when pressure domains close;
14. reopening only after required domains recover;
15. observation of external/non-runner RAM and VRAM pressure;
16. reopening after external applications release resources;
17. persisted paused/running state;
18. process pause/resume;
19. resumable relaunching;
20. safe persistence if a resume launch fails;
21. bounded retry budgets;
22. CUDA-OOM detection with CPU fallback on the next attempt;
23. polling-cadence controls;
24. post-launch resource sampling;
25. batch/backoff controls;
26. log/state/checkpoint directories and persistent state;
27. device-index selection;
28. scheduler admission from current machine pressure rather than a static worker count.

Any future change to resource scheduling belongs in the pinned OPF authority, not in RigorousRAG's scientific catalog.
